# mytask-manager 実装計画 v1.0

[requirements.md](requirements.md)、[screen-design.md](screen-design.md)、[api-design.md](api-design.md)、[db-design.md](db-design.md) に基づく。

## 1. 進め方

- **分担**：実装は Claude が行い、ユーザーはフェーズの終わりに受け入れ確認を行う
- **ブランチ**：フェーズごとにブランチを切る（`phase1-tasks` など）。受け入れ確認で OK が出たら `main` にマージして push する
- **順序**：各フェーズの終わりで「実際に使える状態」になるように並べる。Phase 1 が終われば、繰り返しやサブタスクがなくても日常的に使い始められる
- **確認方法**：フェーズの完了前に、Claude が次の3つを通してから受け入れ確認に回す
  - 自動テスト
  - ビルドと lint
  - ブラウザでの動作確認（Playwright によるスモークテスト）
- **時刻に依存するロジック**：「今日」「期限切れ」「繰り返しの生成」は、`java.time.Clock` を注入して、テストで日時を固定できるようにする

## 2. フェーズ一覧

| Phase | 内容 | 終わったときにできること |
|---|---|---|
| 0 | 環境構築 | 起動コマンド1つで、空の画面とAPIが動く |
| 1 | タスクの基本機能 | タスクの登録・編集・完了・削除、4つのビューで日常的に使える（MVP） |
| 2 | サブタスク | タスクを分解して、進捗を追える |
| 3 | 繰り返しタスク | 定期的なタスクが自動で出てくる |
| 4 | バックアップ | JSONで退避・復元できる |
| 5 | 仕上げ | README・テストの補強・使い勝手の改善 |

## 3. 各フェーズの詳細

### Phase 0：環境構築

**作業**

- **フロントエンド**：
  - Vite で react-ts テンプレートを作成し、以下を導入する
    - React Router
    - TanStack Query
    - React Hook Form
    - Zod
  - テスト環境として Vitest と Testing Library を設定する
- **バックエンド**：
  - Spring Initializr で生成する。依存関係は Web、Data JPA、H2、Flyway、Validation、Lombok
  - Spring Boot 4 で starter の名前が変わっているので、生成時に確認する
- **DB**：
  - `V1__init.sql` に、db-design の3テーブルと全制約を書く
  - データの置き場所は `%USERPROFILE%\.mytask-manager\data`
- **フロントとバックの接続**：Vite の開発サーバーのプロキシで `/api` をバックエンド（8080）に転送する。同じオリジンになるので、CORS の設定は不要
- **起動**：ルートの `start.bat` で、フロントとバックをまとめて起動する
- **その他**：
  - `GET /api/health`
  - 共通のエラーレスポンス（`@RestControllerAdvice`）
  - `.gitignore`

**完了条件**

- `start.bat` を実行すると、ブラウザで空のレイアウト（サイドバーだけ）が表示される
- `/api/health` が応答する
- Flyway のマイグレーションが成功し、データベースファイルがホームディレクトリの下に作られる

### Phase 1：タスクの基本機能（MVP）

**バックエンド**

| 対象 | 内容 |
|---|---|
| タスクAPI | `GET /tasks?view`、`/tasks/counts`、`GET/POST/PUT/DELETE /tasks/{id}`、`PATCH /tasks/{id}/status`、`PATCH /tasks/statuses` |
| 対象外 | サブタスクの関連（`parentId`）はこのフェーズでは常に null として扱う |
| テスト | ビューの判定（期限切れの境界：日付のみ／時刻あり）、並び順、ステータスと `completedAt` の連動 |

**フロントエンド**

| 対象 | 内容 |
|---|---|
| 共通 | 共通レイアウト、サイドバーの件数表示 |
| S1 | 4つのビュー、グループ見出し、クイック追加、完了とトーストの「元に戻す」、完了済みビューの「さらに表示」 |
| S2 | 詳細パネル（サブタスク欄なし）、D4 の未保存確認 |
| 状態表示 | 読み込み中、エラー、0件 |

**完了条件**

- 画面設計の S1・S2 の操作が、サブタスク以外すべて動く
- ここで一度、実際に数日間使ってもらい、気になった点を Phase 5 の候補にためる

### Phase 2：サブタスク

**バックエンド**

- `parentId` 付きの作成と、`NESTED_SUBTASK` のチェック
- 親を削除したときのサブタスクの一括削除
- 一覧API の親単位のまとめと、`contextOnly`・`progress`・`viewDate` の計算
- 409 `SUBTASKS_INCOMPLETE` と、`completeSubtasks` による一括完了
- 完了済みの親の下でサブタスクを未完了に戻したときの、親の差し戻し

**フロントエンド**

- 一覧のインデント表示、開閉、進捗表示、親の薄い表示
- 詳細パネルのサブタスク欄、親とサブタスクの間のパネル切り替え
- D1（一括完了の確認）と D2（親の削除の確認）

**テスト**

- サブタスクだけが条件を満たす場合のビュー判定
- 一括完了と、「元に戻す」での復元
- DB制約による入れ子の拒否（リポジトリ層のテストで確認する）

**完了条件**

- 画面設計のサブタスク関連の操作がすべて動く

### Phase 3：繰り返しタスク

**バックエンド**

- ルールの CRUD、`/rules/preview`
- 発生日の計算ロジック。毎日・毎週・毎月に加え、末日と、31日がない月の扱い
- 生成処理：
  - 実行タイミングは毎日0時・起動時・ルール作成直後
  - `lastGeneratedDate` を使った判定
  - サブタスクのひな形のコピー

**フロントエンド**

- S3 のルール一覧と有効/停止のトグル
- S4 の編集パネルと次回の生成予定の表示
- タスク詳細の「繰り返し」行と、ルールへのリンク

**テスト**（`Clock` で日時を固定して確認する）

- 発生日の計算
  - うるう年の2月
  - 月末（31日指定のルールが30日の月）
  - 開始日・終了日の境界
- 停止中に逃した回は直近の1件だけ生成する
- 削除したタスクを再生成しない
- 二重生成しない

**完了条件**

- 発生日を迎えるとタスクが生成される。日付を変えたテストと、実際の起動の両方で確認する

### Phase 4：バックアップ

- `GET /backup`、`POST /backup/import`（`dryRun` あり）
- S5 の設定画面、D3（置き換えの確認）、最終エクスポート日時の表示
- テスト：エクスポートしたものをインポートして、データが元どおりになること。不正なファイルを拒否すること

**完了条件**

- エクスポートしたファイルで、別の空のDBに完全に復元できる

### Phase 5：仕上げ

- README（起動方法、データの場所、バックアップの方法）
- Phase 1 以降の利用中にためた改善点への対応
- 主要な操作の流れの E2E テスト（Playwright）
- （任意）Windows のログイン時に自動で起動する設定

## 4. リスクと対策

| リスク | 対策 |
|---|---|
| Spring Boot 4 で starter 名や Flyway 連携の設定が 3.x と違う | Phase 0 で実際に生成して確認し、記録に残す |
| ビュー判定と並び順のロジックが複雑になる（サブタスクとコンテキスト表示） | Phase 1 では親だけの単純な形で作り、Phase 2 で拡張する。判定ロジックをサービス層に集め、単体テストで固める |
| 時刻や日付の境界でのバグ | `Clock` の注入と、境界値テストで防ぐ |
| H2 のメジャーバージョンアップでファイル形式が非互換になる | JSON バックアップ（Phase 4）を移行手段にする。H2 のバージョンは pom で固定する |
