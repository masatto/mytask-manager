# mytask-manager DB設計 v1.1

[requirements.md](requirements.md) v1.1 と [api-design.md](api-design.md) v1.0 に基づく。

## 1. 方針

- **DB**：H2（ファイルモード）。接続URLは `jdbc:h2:file:{データディレクトリ}/mytask`
- **スキーマ管理**：Flyway でマイグレーションする（`db/migration/V1__init.sql` から始める）。Hibernate は `ddl-auto=validate` にし、テーブルの自動作成・自動変更はさせない
  - 理由：実際のデータを長く使い続けるので、`ddl-auto=update` に任せると、列の削除や型の変更が意図どおりに行われないリスクがあるため
- **列挙値**：`VARCHAR` に文字列で保存する（`@Enumerated(EnumType.STRING)`）。CHECK 制約で値を制限する
- **日時**：`TIMESTAMP WITH TIME ZONE` に保存する（Java は `Instant`）。API で返すときに +09:00 に変換する
- **日付・時刻**：期限日は `DATE`（`LocalDate`）、期限時刻は `TIME`（`LocalTime`）に保存する
- **ID**：`BIGINT GENERATED BY DEFAULT AS IDENTITY`
  - `BY DEFAULT` にする理由：インポートのとき、バックアップのIDをそのまま入れられるようにするため

## 2. ER図

```
recurrence_rules 1 ──── 0..* rule_subtask_templates
       │
       │ 0..1（ルールを削除したら NULL にする）
       │
     0..*
     tasks ── parent_id ──> tasks（自己参照。1階層まで）
```

## 3. テーブル定義

### 3.1 tasks

| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `id` | BIGINT IDENTITY | × | 主キー |
| `title` | VARCHAR(200) | × | |
| `memo` | VARCHAR(10000) | ○ | |
| `due_date` | DATE | ○ | |
| `due_time` | TIME | ○ | |
| `priority` | VARCHAR(10) | × | `HIGH` / `MEDIUM` / `LOW` |
| `status` | VARCHAR(12) | × | `TODO` / `IN_PROGRESS` / `DONE` |
| `completed_at` | TIMESTAMP WITH TIME ZONE | ○ | |
| `parent_id` | BIGINT | ○ | 親タスク。親を削除するとサブタスクも削除する（ON DELETE CASCADE） |
| `level` | TINYINT | × | 親は 0、サブタスクは 1。入れ子の禁止に使う（3.4 参照） |
| `parent_level` | TINYINT | ○ | サブタスクのときは常に 0。親のときは NULL |
| `recurrence_rule_id` | BIGINT | ○ | 生成元のルール。ルールを削除すると NULL にする（ON DELETE SET NULL） |
| `occurrence_date` | DATE | ○ | 生成元の発生日。繰り返しから生成された親タスクだけが持つ |
| `created_at` | TIMESTAMP WITH TIME ZONE | × | |
| `updated_at` | TIMESTAMP WITH TIME ZONE | × | |

**制約**

| 名前 | 内容 |
|---|---|
| `ck_tasks_due_time` | `due_time IS NULL OR due_date IS NOT NULL`（時刻だけの期限は禁止） |
| `ck_tasks_completed` | `(status = 'DONE') = (completed_at IS NOT NULL)`（完了と完了日時を必ずそろえる） |
| `ck_tasks_priority` / `ck_tasks_status` | 列挙値の制限 |
| `ck_tasks_level` | `(parent_id IS NULL AND level = 0 AND parent_level IS NULL) OR (parent_id IS NOT NULL AND level = 1 AND parent_level = 0)` |
| `uq_tasks_id_level` | `UNIQUE (id, level)`（複合外部キーの参照先として必要） |
| `fk_tasks_parent` | `(parent_id, parent_level)` → `tasks (id, level)`、ON DELETE CASCADE |
| `fk_tasks_rule` | `recurrence_rule_id` → `recurrence_rules (id)`、ON DELETE SET NULL |
| `uq_tasks_occurrence` | `UNIQUE (recurrence_rule_id, occurrence_date)`（二重生成の防止。H2 では NULL 同士は重複とみなさないので、手動作成のタスクは影響を受けない） |

**インデックス**

| 名前 | 列 | 用途 |
|---|---|---|
| `ix_tasks_status_due` | `(status, due_date)` | 今日・今後・期限なしビュー |
| `ix_tasks_completed_at` | `(completed_at)` | 完了済みビュー |
| `ix_tasks_parent` | `(parent_id)` | サブタスクの取得 |

### 3.2 recurrence_rules

| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `id` | BIGINT IDENTITY | × | 主キー |
| `title` | VARCHAR(200) | × | |
| `memo` | VARCHAR(10000) | ○ | |
| `priority` | VARCHAR(10) | × | |
| `due_time` | TIME | ○ | 生成するタスクの期限時刻 |
| `pattern_type` | VARCHAR(10) | × | `DAILY` / `WEEKLY` / `MONTHLY` |
| `days_of_week` | VARCHAR(27) | ○ | `MON,THU` のようにカンマ区切りで保存する。Java では `AttributeConverter` で `Set<DayOfWeek>` に変換する |
| `day_of_month` | INTEGER | ○ | 1〜31、または -1（末日） |
| `start_date` | DATE | × | |
| `end_date` | DATE | ○ | |
| `active` | BOOLEAN | × | |
| `last_generated_date` | DATE | ○ | 最後に生成した発生日（api-design 5章） |
| `created_at` / `updated_at` | TIMESTAMP WITH TIME ZONE | × | |

**制約**

| 名前 | 内容 |
|---|---|
| `ck_rules_pattern` | `DAILY` なら `days_of_week` と `day_of_month` は両方 NULL。`WEEKLY` なら `days_of_week` が NOT NULL で `day_of_month` は NULL。`MONTHLY` なら `day_of_month` が NOT NULL で `days_of_week` は NULL |
| `ck_rules_day_of_month` | `day_of_month IS NULL OR day_of_month = -1 OR day_of_month BETWEEN 1 AND 31` |
| `ck_rules_period` | `end_date IS NULL OR end_date >= start_date` |

- 曜日を別テーブルにしなかった理由：曜日は検索条件に使わず、ルールと一緒に読み書きするだけなので、1列で十分なため

### 3.3 rule_subtask_templates

| 列 | 型 | NULL | 説明 |
|---|---|---|---|
| `id` | BIGINT IDENTITY | × | 主キー |
| `rule_id` | BIGINT | × | ルールを削除すると一緒に削除する（ON DELETE CASCADE） |
| `position` | INTEGER | × | 表示順（0から） |
| `title` | VARCHAR(200) | × | |
| `priority` | VARCHAR(10) | × | |

- 制約：`UNIQUE (rule_id, position)`
- ルールを更新するときは、ひな形を全件削除してから入れ直す（JPA では `orphanRemoval = true` を使う）

### 3.4 サブタスクの入れ子をDBで禁止する仕組み

- サブタスクの行は、`(parent_id, parent_level)` = `(親のID, 0)` で親を参照する
- 参照先は `(id, level)` なので、`level = 0` の行、つまり親タスクしか指せない
- サブタスク自身は `level = 1` なので、別のタスクの参照先にはなれない
- CHECK 制約だけでは他の行の値を参照できないため、この複合外部キーの方法を使う
- アプリ側でも `NESTED_SUBTASK` として先にチェックするので、DBの制約は最後の防衛線という位置づけ

## 4. JPA エンティティとの対応

| テーブル | エンティティ | 補足 |
|---|---|---|
| tasks | `Task` | 親は関連にせず `parentId`（Long）で持つ。サブタスクは親IDの IN 句でまとめて取得する。`level` と `parent_level` は、`@PrePersist` で `parentId` の有無から設定する |
| recurrence_rules | `RecurrenceRule` | `subtaskTemplates` は `@OneToMany(cascade = ALL, orphanRemoval = true)` + `@OrderBy("position")` |
| rule_subtask_templates | `RuleSubtaskTemplate` | |

- 一覧の取得で N+1 問題が起きないように、親とサブタスクは親のIDでまとめて取得する（IN 句）

## 5. データの置き場所

- `%USERPROFILE%\.mytask-manager\data\mytask.mv.db` に置く
  - 理由：リポジトリの外に置くので、`git clean` やリポジトリの作り直しでデータが消えない
- `application.yml` の `mytask.data-dir` で上書きできるようにする
